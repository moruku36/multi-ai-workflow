# Render Workflowsの活用案

[English](render-workflows-proposal.md) | [日本語](render-workflows-proposal.ja.md)

状態：**提案のみ**。公開公式資料の確認日：2026-11-05（UTC）。SDK導入、デプロイ、API経路の認可、レビュー品質の受入、ライブ自律運用を確認した記録ではありません。既存の日付付きアーキテクチャ記録は変更しません。

## マルチAIワークフローでの位置づけ

Render Workflowsを、範囲を限定したオンデマンド処理の実行層として検討します。公開情報の収集、認可済みモデルAPIの呼び出し、結果の統合、人による受入のための証跡返却などが候補です。常駐の調整役、メールボックス、リポジトリのレビュー規約を置き換えるものではありません。

想定する流れは、認可済み依頼 → 範囲・予算の検証 → 公開入力の収集 → 件数を限定したprovider別タスク → 指摘の統合 → 証跡記録 → 調整役の確認です。実行成功は、公開・マージ・送信・デプロイの許可ではありません。別インスタンスでの実行だけでは独立レビューにならず、実際のproviderとレビュー対象revisionの一致が必要です。

具体例は、公開資料の比較、外部送信許可済み資料からのドラフト、公開コードの限定レビューです。最初は無害なfixtureを使い、実モデル呼び出しは行いません。この提案の入出力には私的会話、個人情報、秘密を含めません。

## 製品の境界

[Render公式概要](https://render.com/docs/workflows)では、Python／TypeScriptのtaskとflow、管理されたキュー、必要時のインスタンス起動、再試行、実行状況の確認を説明しています。taskは別taskを連鎖実行でき、flowは順序付きstepの結果を保存して再実行時に再利用します。同じAPIとは扱いません。現在の概要ではflowからtask／flowへの連鎖は未対応です。runは外部から接続するポートを公開しません。全run完了後に実行基盤がゼロへ縮退しても、関連費用がすべて消えるとは限りません。

Workflowsは、常時動くbackground workerやcron jobとは別です。ネイティブの定期実行は現在未対応とされ、定期起動には別schedulerと別途承認が必要です。本提案はオンデマンド起動のみです。

## RenderとVercelの使い分け

| 選択肢 | 検討する理由 | 追加確認事項 |
| --- | --- | --- |
| Render Workflows | タスク中心の独立実行、taskごとのcompute設定、ユーザー向けアプリの外に実行境界を設ける | 現行SDK、region、quota、状態保持、task／flow制約、ジョブ全体の費用 |
| Vercel Workflows | Vercel上の既存アプリと密接な永続的な複数段階処理 | workflow／step制限、デプロイとの結び付き、保持期間、プラットフォーム全体の費用 |
| 既存経路の維持 | 小規模で動作済みの処理なら新基盤を増やさない | 時間、再試行、監査、費用の要件を満たすか |

[Vercelにも永続ワークフロー](https://vercel.com/docs/workflows)があり、再試行、状態保存、待機・再開に対応します。単なるフロントエンドの置き場とは扱いません。アプリをVercel、特定ジョブをRenderとする分担は候補ですが、認証・監視・障害境界が増える負担に見合う場合に限ります。移行決定や最安という結論ではありません。

## ライブ試行前の予算設計

記憶上の無料枠ではなく、現行の[Render制限・料金](https://render.com/docs/workflows-limits)を参照します。runのcompute、run／stepの状態保持、該当する外向き通信が課金対象です。外部モデルAPI、追加storageやschedulerの費用は別です。固定computeプランは実行時間、flexはCPU／RAM使用量に基づき、最低課金もあります。親子run、再試行、失敗した試行も数えます。ゼロへの縮退で状態保持や他サービスの請求が消えるわけではありません。

承認前に、請求通貨でジョブ全体を見積もり、run数・分岐数、同時実行数、timeout、再試行回数、入出力サイズ、providerごとのtoken上限、総費用上限を指定します。providerの制限や通知だけで総額上限が強制されるとは考えません。アプリ側の受付・停止制御を検証し、残予算や単価が不明なら次のrunを開始しません。外部応答の結果が不明なまま再試行すると、副作用も請求も重複するおそれがあります。

## 認証・秘密・安全な運用

- 将来の呼び出し元は、起動前に依頼者の認証と認可を確認します。task名・入力schemaを制限し、重複依頼やreplayを拒否します。許可する操作は任意のモデル出力ではなく呼び出し元が判断します。
- Render用とモデルprovider用の認証は別です。承認済みのサーバー側secret管理と最小権限を使います。ブラウザー側コード、リポジトリ、run引数、戻り値、ログに認証情報を置きません。認証情報の作成や継続アクセスの付与は別途承認が必要です。
- 引数、出力、エラー、traceは保持され得るデータです。送信前に除去・秘匿し、機密文書を埋め込む代わりに認可済み成果物を参照します。公開入力以外へ広げる前に保持・アクセス条件を確認します。
- 副作用には回数制限付き再試行と冪等性を設けます。cancelやtimeoutは外部操作の未実行を証明しません。結果確認後に再試行を判断します。
- タスク結果は新しい権限を与えません。公開、GitHubマージ、デプロイ、重大な操作には既存の承認とゲートを維持します。

## 導入と証跡のチェックリスト

1. 互換SDKを固定し、公開／合成fixtureを1つ定義します。期待結果と失敗ケースを記録します。
2. クラウドへのデプロイ、新認証情報、有料provider呼び出しなしでローカル確認します。revisionとコマンドを記録し、mock成功はローカル証拠に限定します。
3. 構築やライブ呼び出しの前に、workspace、region、送信先、認証・アクセス、試行予算、停止条件を別途承認します。
4. 承認後に限定試行を1回行い、開始・終端状態、秘匿済み出力、再試行・失敗時の動作、実測総費用を記録します。run IDの発行だけでは完了ではありません。
5. リポジトリ変更の受入や運用拡大の前に、対象headに対する別providerレビューと決定的検査を完了します。[レビュー規約](pr-review-pipeline.ja.md)に従います。
6. 文書化、ローカル試験、デプロイ、実行、受入を区別します。証跡・権限・予算が不足すれば拡大を止めます。

この文書変更ではRenderサービス、scheduler、デプロイ、API認証情報、有料workloadを作成せず、runtimeやリポジトリのセキュリティ設定も変更しません。
