## 3. 不採用および保留項目と理由

本提案では、効率化の名の下に安全性や検証可能性を損なう以下の提案を明示的に不採用または保留とする。

1. **会話全文の再送（不採用）**:
   - *理由*: トークン消費量が指数関数的に増大し、コンテキスト枠を圧迫する。また、過去の会話に含まれる不要な試行錯誤や秘匿情報が別環境へ流出するリスクがある。差分・成果物参照・構造化要約で代替する。
2. **未検証の live quota 自動振分け・周期ポーリング（保留・不採用）**:
   - *理由*: live クォータ API や画像自動認識の信頼性が検証されておらず、誤った残量判断によりタスク中断や誤ルーティングを招く恐れがある。定期ポーリングによる無駄な API 消費も回避する。
3. **自動承認および自動マージ（不採用）**:
   - *理由*: 安全境界、権限管理、品質担保のため、Product Owner / 人間による最終受入ゲートを必須とする。
4. **Legacy chain (`tools/pipeline.py`) の常時採用（不採用）**:
   - *理由*: 該当スクリプトは旧運用の Legacy であり、現行のワークフローとは異なる。無断での置換や本番化は行わない。
5. **モデルラベル = runtime ID とした課金推定（不採用）**:
   - *理由*: 運用上の呼称（ラベル）と実際の runtime API ID は一致しない場合がある。観測証拠のない課金推定は不正確な混乱を招くため、`requested` と `observed runtime` を厳格に分離する。
6. **品質ゲートの削減・省略（不採用）**:
   - *理由*: トークン削減や速度向上のために CI チェックや別 provider レビューを省略することは、リポジトリの品質基準に反する。
7. **MiMo 提案の固定 N ターン / 固定 2 リトライ / タスク=head SHA 一律定義（不採用）**:
   - *理由*:
     - *固定 N ターン*: タスクの性質により必要な文脈量が異なるため、一律指定は文脈の切断または無駄なトークンを招く。
     - *固定 2 リトライ*: 既存ルールの「通常失敗後に認可済み代替1候補を検討（最大1回の代替）」との整合を主因として不採用。承認なくリトライ回数を増やすことは認めず、権限拒否や安全境界違反の発生時は常に即時停止（fail-closed）する。
     - *タスク = head SHA 一律定義*: 調査・設計・議論など、直ちにコミットを伴わないタスクが存在するため。

## 4. ローカル改善案の詳細設計（提案優先度と実装状態別）

### 提案優先度 P0: 必須・安全性・基本ゲート（運用文書反映済み）

#### 4.1 コンテキスト最小化原則 (`docs/handoff-templates.md`) 【運用文書反映済み】
- 引き継ぎ時は会話ログ全体を複製せず、次の3要素を基本とする:
  1. **直前コミット/成果物の参照**: ファイルパス、コミット SHA、diff。
  2. **構造化された現状要約**: 目的、達成状況、未解決の課題。
  3. **次の一歩の明確化**: 次の担当者が行うべき最小限の作業範囲と完了条件。
- 機械的な「直近 N ターン」の切り出しは義務付けず、タスクの文脈に応じた最小限の抜粋とする。

#### 4.2 Flash 中心ルーティングと昇格・降格イベント (`docs/routing-guide.md`, `AGY_RULES.md`) 【運用文書反映済み】
- **平常時**: Gemini 3.8 Flash をベースモデルとして調査、モック、実装、軽微な修正を担当。effort（Low/Medium/High等）は普遍的な既定値とせず、タスクの性質や本人指定時に個別に選択・記録する。
- **昇格イベント（上位モデルへの委託）**:
  - 同一のエラー・失敗が再現され、Flash で解決の見込みが立たない場合。
  - 合意した作業上限（例: 試行上限や時間枠）に達しても具体的な進捗がない場合。
  - 複雑なアーキテクチャ設計や、極めて高度な独立推論が必要な場合。
- **降格イベント（通常モデルへの復帰）**:
  - 上位モデルによって難所・ブロック要因が解消された直後。
  - 上位モデルでの作業上限に達した場合（未解決時は作業を保存して中断）。
  - 後続の定型作業（テスト拡充、ドキュメント整形、タイポ修正等）へ移行した段階。
- **記録ルール**: `requested model/effort` と `observed runtime model/effort` を別々に記録し、証拠がない場合は `UNKNOWN` とする。

#### 4.3 失敗ハンドリングと上限設定 (`docs/handoff-templates.md`) 【運用文書反映済み】
- 失敗原因を次の4つに分類して記録する:
  1. `環境エラー (Environment)`: 一時的な通信障害、サービスダウン等。
  2. `権限拒否 (Authorization)`: 実行環境や API の権限不足、安全境界違反。
  3. `タイムアウト (Timeout)`: 応答停止、作業上限超過。
  4. `品質未達 (Quality)`: 出力が受入基準を満たさない、テスト失敗。
- **対応方針**:
  - `権限拒否` の場合は即時停止 (fail-closed)。別経路や別 ID での迂回再試行は禁止。
  - `環境エラー` や `品質未達` の場合、通常の受け渡し失敗は1回で原因を保存し、別の認可済み候補1つを検討（最大1回の代替）。無制限なリトライループは禁止。

#### 4.4 並列度と終了条件の維持 (`docs/routing-guide.md`, `docs/pr-review-pipeline.md`) 【運用文書反映済み】
- **並列度**: 最大2つの独立タスクまで（人間による手動管理の範囲）。自動並列実行機能とは混同しない。
- **終了条件**:
  - レビュー対象 head SHA と検証 head SHA の完全一致。
  - 必要な静的検査・CI の成功。
  - 重大な指摘 (Blocker / Major) の解消。
  - Product Owner / 人間による受入確認。

### 提案優先度 P1: 効率化・構造化（運用文書反映済み／未実装提案の区分）

#### 4.5 handoff テンプレートの使い分け基準 (`docs/handoff-templates.md`) 【運用文書反映済み】
- **短い進捗受渡し（4項目）を適用するケース**:
  - 同一環境内での通常進捗報告。
  - 単一ファイル修正、タイポ修正、調査結果の要約など、低リスクかつ安全境界を跨がない作業。
- **詳細 Evidence manifest を適用するケース**:
  - モデル間・provider 間のエスカレーションやハンドオフ。
  - 外部サービスへの出力、認証や権限に関わる操作。
  - handoff 失敗・例外の記録。
  - 複数段階のパイプライン処理。

#### 4.6 レビュー区分の明文化 (`docs/pr-review-pipeline.md`) 【運用文書反映済み】
- **通常文書 (Normal Docs)**:
  - 対象: ドキュメントの誤字脱字修正、フォーマット調整、軽微な表現推敲。
  - レビュー: 軽量レビュー（静的チェック + 単一レビュアー確認）。重複レビューは回避。
- **重要設定文書 (Critical / Governance Docs)**:
  - 対象: 権限設定、安全境界、運用ルール (`routing-guide`, `ai-team` 等)、セキュリティ関連。
  - レビュー: 厳格レビュー（別 provider 独立レビュー + 人間の最終承認）。

#### 4.7 イベント駆動のクォータ観測 (`docs/dots-codexbar-orchestration.md`) 【未実装提案・将来検証】
- 定期ポーリングは行わず、以下のイベント時のみ手動観測を行う:
  - タスク開始前（キャパシティ確認）。
  - モデル昇格・エスカレーション検討時。
- 観測時刻から時間が経過しているもの、または未取得のものは `unknown` と記録し、一律の自動実行停止ではなく明示的な手動選択・手動確認に戻す。

#### 4.8 決定的な静的処理の先行とキャッシュ仮説評価 (`tools/pipeline.py`) 【未実装提案・将来検証】
- **静的処理の決定性**:
  - SHA ハッシュ照合、Markdown リンク切れ、末尾空白、Evidence manifest のスキーマ検査は、LLM を使わずシェルやローカルスクリプトで機械的に実行する。
- **Prompt Cache の仮説評価**:
  - 入力プロンプトの固定部分（システム指示、固定参照資料）が大きく、利用 provider がプロンプトキャッシュをサポートし、かつ秘密情報を含まない場合に限り、キャッシュ有効化を検討。
  - パイロット測定において cache hit 率を測定し、費用対効果を評価する。

## 5. 測定・検証フレームワーク（仮説評価）

本フレームワークは、効率化の効果を客観的に評価するためのパイロット測定設計案である。現時点で実測データは未提供・未確認であり、効果や削減率を保証するものではない。

### 5.1 記録メトリクス（タスク単位）
各タスクごとに以下の項目を記録する（数値は取得できる時のみ記録）:

| メトリクス項目 | 記録内容・形式 | 目的 |

| `subscription_quota_obs` | サブスクリプション枠の観測値（観測窓および観測時刻、不明は unknown） | サブスク枠の観測（API課金と混算しない） |
| `api_usage_billing` | API使用量および課金情報（取得可能な場合のみ記録） | 従量課金の把握（サブスク枠と合算・混算しない） |

| `retry_count` | リトライ回数と失敗分類 (`env`, `auth`, `timeout`, `quality`) | 失敗傾向の把握 |
| `review_rounds` | レビュー往復回数 | 手戻り工数の測定 |
| `cache_hit` | キャッシュヒットの有無・比率（対応環境のみ） | キャッシュ効果の検証 |
| `human_effort_minutes` | 人間による確認・指示・介入時間（分） | 人間工数の把握 |
| `unknown_rate` | runtime や quota が `unknown` だった割合 | 観測精度の評価 |
| `quality_outcome` | `accepted` / `reworked` / `rejected` | 品質ゲート通過状況 |

### 5.2 パイロット測定設計案
- **対象規模**: 2週間、または先行する 10タスク。
- **位置づけ**: 固定の合否判定基準ではなく、運用の実現可能性とデータ収集精度を確認するためのサンプル設計案。
- **検証項目**:
  - Flash 中心運用でタスクが円滑に完了するか。
  - 不必要な上位モデル昇格が発生していないか。
  - 差分中心の handoff により、トークン消費や情報欠落がどのように変化するか。
  - `unknown` 記録の頻度と運用の阻害要因。

## 6. 安全・品質・承認ゲートの維持

1. **fail-closed と手動確認の切り分け**: 権限拒否や安全境界違反は即時停止 (fail-closed) し、別経路での迂回は行わない。一方でランタイムやクォータの事実上の未知については `UNKNOWN` / `unknown` と記録した上で、自動停止ではなく明示的な手動選択・手動確認へ移行する。
2. **監査性の維持**: Evidence manifest における revision、ハッシュ、承認段階の記録を省略しない。
3. **機密情報の完全排除**: 公開リポジトリおよびレポートには、個人情報、認証情報、私的な会話ログ、内部接続情報、課金画面の生データを含めない。
4. **段階の分離**: ユーザー承認、ローカルテスト、CI チェック、本番マージはそれぞれ独立した証拠として扱い、同一視しない。

## 7. 2026-10-19 実運用効率化チェックリスト（5項目）

日々のタスク実行時に遵守する、5項目に集約した実運用チェックリスト:

1. **反復調査の排除**: 完了タスクや不変の成果物を反復調査・再取得しない。成果物に変更が生じた場合、または失敗・例外発生時のみ再確認を行う。
2. **差分・成果物中心の引き継ぎ**: 会話全文の再送を禁止する。目的・現状・根拠・次の一歩と必要な差分（ファイルパス / コミットSHA / diff）のみを伝達する（固定Nターンの義務化はしない）。
3. **結果通知中心の進捗管理**: 途中経過の不要なチャット往復を抑制し、検証可能な成果物と完了結果の通知を中心とする（未実装の自動通知機能は主張しない）。
4. **失敗原因の分類と停止原則**: 同一失敗を漫然と繰り返さない。原因（環境エラー / 権限拒否 / タイムアウト / 品質未達）を記録・保存し、認可済みの代替1候補を検討する（最大1回の代替）。権限拒否・安全境界違反時は常に即時停止 (fail-closed) する。
5. **手動最大2並列と計測分離**: 手動管理下で最大2つの独立タスク上限を維持する。サブスク枠観測（窓と時刻）とAPI使用量・課金情報を別フィールドで記録し、混算・合算を禁止する（数値は取得時のみ記録、unknown可）。
